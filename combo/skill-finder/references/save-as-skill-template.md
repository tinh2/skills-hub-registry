# Save As Skill Template

Phase 5 of the orchestrator. When the user opts to save a completed chain as a reusable skill, the orchestrator fills in this template and hands the result to `skills-hub-registry-skillify` for publish.

## Why a Template

The orchestrator does not invent a skill from scratch. Inventing produces inconsistent skills with drift between authors. The template guarantees every saved chain produces a skill with the same shape, same frontmatter fields, same composition declaration, and the same trigger phrase style.

## Who Actually Creates The Skill

**Skill Finder fills this template. Skillify creates the skill.** The orchestrator is responsible for producing a clean, validated SKILL.md body plus the structured metadata. The `skills-hub-registry-skillify` skill is responsible for everything after: writing the file to the skills directory, assigning a version, scoping it (user, org, public), checking for name collisions, and publishing to skills hub.

This boundary is non negotiable. If Skill Finder tries to write a SKILL.md directly to `~/.claude/skills/<name>/SKILL.md` or push to skills hub through any other tool, the resulting skill bypasses skillify's checks and ends up inconsistent with the rest of the catalog.

## When to Use

Phase 5 step 4c. After the user said `y` to "save this workflow as a reusable skill" and confirmed the name and description.

## Filling the Template

The orchestrator reads the plan file and extracts:

* **`<NAME>`.** The user confirmed kebab case name. Default: task slug plus `-pipeline`.
* **`<DESCRIPTION>`.** The user confirmed one line description. Default: a templated summary.
* **`<TASK>`.** The original task statement from the plan file.
* **`<STEP_LIST>`.** The ordered child skill slugs from the executed plan, in order, with their step labels.
* **`<TRIGGER_PHRASES>`.** Derive from the task statement plus the patterns from `workflow-patterns.md` that originally matched. Five to eight phrases.
* **`<HANDOFF_NOTES>`.** Lifted verbatim from the plan file `## Handoffs` section.
* **`<NEXT_STEPS_LIKELY>`.** The detector hits from Phase 6, captured so the new skill can suggest them too.

## The Template

```markdown
---
name: <NAME>
description: <DESCRIPTION>
version: 1.0.0
category: combo
triggers:
  - <TRIGGER_PHRASE_1>
  - <TRIGGER_PHRASE_2>
  - <TRIGGER_PHRASE_3>
  - <TRIGGER_PHRASE_4>
  - <TRIGGER_PHRASE_5>
composition:
  type: chain
  steps:
    - label: <STEP_1_LABEL>
      skill: <STEP_1_SKILL>
      required: true
    - label: <STEP_2_LABEL>
      skill: <STEP_2_SKILL>
      required: true
    - label: <STEP_N_LABEL>
      skill: <STEP_N_SKILL>
      required: false
---

# <NAME>

<DESCRIPTION>

## What This Skill Does

When invoked, this skill replays a tested workflow. The chain was captured on <DATE_CAPTURED> from a successful run by Skill Finder.

Original task that produced this chain:

> <TASK>

## Workflow

This skill runs the following steps in order. Each step receives a structured handoff from the prior step (see [handoff-protocol](https://skills-hub.ai/skills/skill-finder/references/handoff-protocol.md)).

<STEP_LIST>

For each step, the chain:

1. Builds context from the prior step's handoff.
2. Invokes the step's skill.
3. Classifies the outcome.
4. Retries once on failure.
5. Pauses and asks the user if the retry also fails.

## When to Invoke

Use this skill when the task matches one of these phrases:

<TRIGGER_PHRASES>

## Handoffs Between Steps

<HANDOFF_NOTES>

## What Happens After

When the chain completes, the skill scans for follow ups. Common ones from the original chain:

<NEXT_STEPS_LIKELY>

## Customization

To adapt this skill to a different project, fork it and edit the `composition.steps` list. Each step references a child skill by slug. Replacing a slug swaps in a different implementation. The handoff protocol stays the same.

## Provenance

This skill was generated by Skill Finder v2 on <DATE_CAPTURED>. Original plan file: `<PLAN_FILE_PATH>`.
```

## After Filling

**Skill Finder must hand the filled template to skillify. It must not write a SKILL.md to the local skills directory itself and it must not publish to skills hub via any other tool.** Skillify owns skill creation. Skill Finder owns the chain.

1. Write the filled template to a temp path: `/tmp/skill-finder-save-<NAME>.md`.
2. Invoke skillify via the Skill tool:

   ```
   Skill(
     skill="skills-hub-registry-skillify",
     args="""
     Create a new skill from the filled SKILL.md at /tmp/skill-finder-save-<NAME>.md.

     Name: <NAME>
     Description: <DESCRIPTION>
     Category: combo
     Triggers: <comma list of trigger phrases>
     Child skills (ordered): <comma list of step skill slugs>
     Provenance: Skill Finder v2, plan file <PLAN_FILE_PATH>

     Use the SKILL.md body as written. Do not regenerate.
     """
   )
   ```

3. Skillify handles version, scope, name collision logic, the actual write to the skills directory, and the publish to skills hub.
4. Capture the published URL from skillify's response.
5. Report the URL to the user.

If skillify returns an error, surface the error verbatim. Do not retry skill creation by writing files directly. The user fixes the input or skips Phase 5.

## Validation Before Handoff

Before handing to skillify, the orchestrator does a quick sanity check:

* `<NAME>` matches `^[a-z][a-z0-9-]+[a-z0-9]$`.
* `<DESCRIPTION>` is between 20 and 200 characters.
* `<STEP_LIST>` has at least 2 entries.
* All `<STEP_N_SKILL>` slugs exist (either in the local catalog or successfully found via `search_skills`).
* Trigger phrases are at least 3 entries.

If any check fails, abort the save and tell the user which check failed. Do not call skillify with a broken input.

## Composition Type

The template uses `composition.type: chain`. Future versions may support:

* `chain` (this version): sequential, with handoffs.
* `parallel`: independent steps, no handoffs.
* `tree`: branching based on step output.

For v2, only `chain` is supported.
